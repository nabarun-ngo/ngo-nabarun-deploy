Automatic run: the public site is rebuilt in production on the 1st and 15th of every month at 02:00 UTC, using the newest stable tag on main. It fetches content at build time, so the rebuild refreshes content even without a new release. Nothing deploys to stage on a schedule, and every other deployment is manual.

2. Collect access before changing settings

  • Admin access to the deploy GitHub repository.
  • Read access to both application repositories.
  • Permission to manage the stage and production Google Cloud projects.
  • Permission to create service accounts and JSON keys.
  • Permission to manage the backend-api and frontend Doppler projects and their stg/prd configs.
  • Names of the people or teams who will approve stage and production deployments.

3. Prepare Google Cloud and Firebase

  1. Choose the stage and production project IDs

    Record the Google Cloud project ID used by each environment. The current workflows call this value GCP_PROJECT_ID for the backend and FB_PROJECT_ID for the frontends. They may be the same project ID, but they are separate GitHub secret names.

  2. Enable the required services

    In each applicable Google Cloud project, enable:

    • App Engine, Cloud Build, and Cloud Storage for the backend.
    • Firebase and Firebase Hosting for the frontends.

    Create the App Engine application once in each backend project. Create or connect the Firebase project once in each frontend project.

  3. Create the Firebase Hosting sites

    Make sure these site IDs already exist before the first deployment:

    • Stage: ngonabarun-portal-stage and ngonabarun-stage
    • Production: ngonabarun-portal and nabarunngo

  4. Create a backend deployment service account

    Create one service account per environment where possible. It must be allowed to deploy App Engine versions, inspect versions, move service traffic, start Cloud Build, upload the App Engine staging bundle, and act as the App Engine runtime service account.

    A practical starting permission set is App Engine Admin, Cloud Build Editor, Storage Admin, and Service Account User. Your cloud administrator can reduce these permissions after a successful deployment by checking the audit logs.

    Create a JSON key and save the complete JSON temporarily. This becomes GCP_SA_KEY.

  5. Create a frontend deployment service account

    Create one service account per environment. Grant it permission to deploy Firebase Hosting releases for both Hosting sites in that environment. Create a JSON key and save the complete JSON temporarily. This becomes FB_SA_KEY.

Protect JSON keys. Never commit a service-account JSON file. After adding its full contents to GitHub, securely delete local copies. Rotate the key immediately if it is pasted into a ticket, chat, log, or source file.

4. Prepare Doppler projects, configs, and tokens

  1. Confirm the projects and configs

    Doppler projectStage configProduction configUsed by
    backend-apistgprdBackend migration and App Engine runtime
    frontendstgprdInternal portal and public site builds

  2. Add application configuration

    Copy the required names from each application's .env.example into the matching Doppler config. Use real stage values in stg and real production values in prd.

    • Backend project: database, Redis, application URLs, CORS, Auth0/JWT, Google, Firebase storage, email, OneSignal, and alerting configuration.
    • Frontend project, internal portal: every required NG_APP_* value. Never enable auth bypass or mock data in stage or production.
    • Frontend project, public site: required NEXT_PUBLIC_* values plus server-only values such as API_KEY. Put these in the same frontend config as the portal values.
    Frontend values prefixed with NG_APP_ or NEXT_PUBLIC_ are compiled into browser files. They must not contain private keys, client secrets, or passwords.

  3. Create one read-only service token per project and config

    One frontend token covers both the internal portal and the public site because they share the frontend project. Do not reuse a stage token in production. The test pipeline needs its own tokens for its Doppler project in tests-stage, tests-prod, and tests-scheduled.

5. Configure GitHub

  1. Enable Actions permissions in the application repositories

    In both the backend and frontend repositories, open Settings → Actions → General → Workflow permissions. The release workflow creates tags and GitHub Releases, so allow the workflow the write permissions declared in its YAML.

    A push to develop creates a prerelease tag. A push to main creates a stable tag. Confirm at least one suitable tag exists before using latest in a deploy.

  2. Create GitHub Environments in the deploy repository

    Open Settings → Environments and create these exact names. Frontend and backend have separate environments, so every workflow reads the same secret names and a frontend job never sees backend credentials.

    Names follow <tier>-<target>: the tier is fe, be, or tests, and the target is stage or prod. An auto-approved copy for scheduled runs adds -scheduled, for example fe-prod-scheduled. Use lowercase letters, digits, and hyphens only. Each application declares its names in its manifest; test runs declare theirs in config/schedules/tests.json. The full convention is in docs/platform.md under "Naming GitHub Environments".

    Create each environment here before any manifest or schedule refers to it, and copy the name exactly. If a name is misspelled, GitHub quietly creates a new environment with no reviewers and no secrets, and the deploy runs without approval. No automated check catches this, so compare names carefully.
    EnvironmentProtectionPurpose
    fe-stageAt least one required reviewer.Manual frontend stage deployments
    fe-prodRelease-manager reviewers; deployment branches limited to main.Manual frontend production deployments
    fe-prod-scheduledNo reviewer; deployment branches limited to main.Automatic public-site production rebuild
    be-stageAt least one required reviewer.Manual backend stage deployments, GCP operations and cleanup
    be-prodRelease-manager reviewers; deployment branches limited to main.Manual backend production deployments, GCP operations and cleanup

    The test pipeline uses tests-stage, tests-prod, and tests-scheduled; they are not needed for frontend or backend deployment.

    Only the public site can use fe-prod-scheduled: it is the only application listed in config/schedules/deploys.json, the file that declares scheduled deploys. The pipeline rejects a scheduled deploy for any application not listed there, so the internal portal and backend always need a reviewer for production.

    Inside each Environment, open Environment secrets and add:

    GitHub secrets are case-sensitive. Keep the exact uppercase names. fe-prod-scheduled must hold copies of the fe-prod secrets because GitHub Environments do not share secrets. When you rotate a production frontend credential, update both environments.

  4. Decide whether a GitHub PAT is needed

    Do not manually create a secret named GITHUB_TOKEN. GitHub automatically creates that token for each workflow run.

    The deploy workflows use the automatic token to read public application repositories. If either application repository is private, create a fine-grained personal access token with read-only access to repository contents and metadata for those repositories. Add it to the deploy repository as a repository secret named PAT.

    Use PAT only for cross-repository read access. It is optional for the current public application repositories and is not the same as DOPPLER_TOKEN.

6. Run the first deployments safely

  1. Confirm a releasable tag exists

    For stage, confirm a semver prerelease tag such as 1.2.0-beta.1 is reachable from develop. For production, confirm a stable tag such as 1.2.0 is reachable from main.

  2. Deploy the backend to stage

    In the deploy repository, open Actions → Ops — Deploy Backend (GAE) → Run workflow.

    manifest_name: backend
target_environment: stage
tag_name: latest

    Approve the be-stage Environment. The workflow builds the selected tag, runs the database migration and seed through Doppler, deploys a zero-traffic App Engine version, checks /health, and only then moves traffic.

  3. Deploy both frontends to stage

    Open Actions → Ops — Deploy Frontend (Firebase) → Run workflow and run it twice:

    manifest_name: fe-internal-app
target_environment: stage
tag_name: latest

manifest_name: fe-public-site
target_environment: stage
tag_name: latest

    Approve each fe-stage run. Doppler injects environment values while each frontend is built, then the output is deployed to its Firebase site.

  4. Verify stage before production

    • Backend health endpoint returns HTTP 200.
    • Database migrations completed and expected seed data is present.
    • Internal portal login, API URL, and service worker are correct.
    • Public-site canonical URL, API calls, forms, and no-index setting are correct.
    • No secret value appears in GitHub logs or frontend browser files.

  5. Deploy production

    Repeat the same workflows with target_environment: prod. Use latest to select the newest stable tag reachable from main, or enter an explicit stable tag. A reviewer must approve be-prod or fe-prod.

    After the first production public-site deploy, the scheduled rebuild runs on the next 1st or 15th through fe-prod-scheduled without approval. Check that run in the Actions tab; if it fails, compare its secrets with fe-prod.

7. Fast troubleshooting

FailureMost likely check
Cannot list tags or checkout application sourceRepository visibility and the optional PAT; also confirm the tag is on the expected branch.
No tag found for latestStage needs a reachable prerelease tag on develop; production needs a reachable stable tag on main.
Doppler access denied or config not foundDOPPLER_TOKEN in a fe-* environment must read project frontend; in a be-* environment it must read backend-api. The config must be stg for stage and prd for production.
Frontend compilation reports a missing variableRequired NG_APP_* or NEXT_PUBLIC_* value in the shared frontend config.
Backend migration failsDATABASE_URL, database network access, bundled Doppler CLI, and migration permissions.
App Engine authentication or permission errorFull JSON in GCP_SA_KEY, matching GCP_PROJECT_ID, enabled APIs, and service-account roles.
Backend deploy succeeds but health check failsRuntime Doppler values, application logs, /health, and database/Redis reachability. The new version remains at 0% traffic.
Firebase site or project not foundFB_PROJECT_ID, Hosting site IDs in the manifest, and FB_SA_KEY permissions.
Scheduled public-site deploy fails but manual production worksMissing or stale copies of FB_PROJECT_ID, FB_SA_KEY, or DOPPLER_TOKEN in fe-prod-scheduled, or its branch rule does not allow main.
"Scheduled deploys are only allowed for fe-public-site to prod"The schedule was changed to another application or to stage. Only the public-site production rebuild may run on a schedule.
Deploy runs without asking for approval and then fails on an empty secretThe environment was never created in GitHub. GitHub creates a referenced environment that does not exist, with no reviewers and no secrets. Delete that auto-created environment, then create it properly with the exact name, reviewers and secrets.

8. Final setup checklist

  • App Engine and Firebase Hosting resources exist.
  • All four Firebase Hosting site IDs exist.
  • Backend and frontend service-account JSON keys are stored only in GitHub Environment secrets.
  • Doppler has backend-api and one shared frontend project, each with stg and prd.
  • The internal portal and public site values are both stored in frontend.
  • Each DOPPLER_TOKEN is a read-only service token for the right project and config.
  • GitHub Environments fe-stage, fe-prod, fe-prod-scheduled, be-stage, and be-prod exist with exact names.
  • All four manual environments have required reviewers; both production environments and fe-prod-scheduled allow only main.
  • fe-prod-scheduled secrets match fe-prod.
  • The old stage, prod, and stage-scheduled environments are deleted after the new ones work.
  • All required Environment secrets are present and correctly cased.
  • A suitable application release tag exists.
  • Backend, internal portal, and public site have each passed a stage deployment.
